# 디자인 크리틱 — MCP Monitor 웹 UI (Plan 3 Task 16)

**스킬:** `design:design-critique`(틀), `audit-suite:make-interfaces-feel-better`(마감 점검표), `audit-suite:audit-as-{design-eng,ux-eng,perf-eng,frontend-eng}`(관점별 점검) · **날짜:** 2026-11-06

**입력:** Task 15 기준 이미지 14장(board, login, dashboard, mcp-list, mcp-detail, notice-editor, notice × dark/light), 같은 백엔드에서 찍은 640×400·320×200 화면 13장씩, 명령 팔레트·404 화면, 그리고 `docs/design/direction.md`(고성능 HMI 관제 콘솔: 색은 상태에만, 정상은 조용하게, 보드는 멀리서·관리는 촘촘하게). 단계: 출시 전 마감(최종).

## 1. 첫인상 (2초)

- **보드:** 눈이 먼저 가는 곳은 판정 문장("모든 MCP가 정상이에요")입니다. direction.md가 정한 "한 군데의 대담함" 그대로이고 맞는 선택입니다. 그다음이 카드의 이름과 배지입니다.
- **관리 화면:** 첫눈에 h1, 그다음 표나 폼입니다. 사이드바는 무채색이라 본문과 경쟁하지 않습니다.
- **문제:** MCP 목록·상세·보드 카드에서 **정상 배지가 초록 채움**이라, 정상 행에도 색이 칠해져 있었습니다. direction.md §2("화면에 색이 보이면 그것은 언제나 문제")와 screens/mcp.md("정상은 작은 초록 아이콘")와 어긋났고, 행이 많아지면 "색 있는 칸 = 문제" 훑기가 깨집니다. → **고침**(§7-1).

## 2. 위계

| 화면 | 읽는 순서 | 판단 |
|---|---|---|
| 보드 | 판정 문장 → 문제 카드(위로 정렬, 상단 띠·soft 채움) → 정상 카드 | 좋음. 정상 배지를 조용하게 바꾼 뒤 문제 카드의 대비가 더 커짐 |
| 대시보드 | MCP 요약(0인 칸은 점선·muted, 0이 아닌 칸만 링크) → 현재 세션 → 최근 이슈와 조치 → 준비 중 카드 2개 | 좋음. 준비 중 카드는 점선 + 모래시계 한 줄로 가짜 데이터 없이 비어 있음 |
| MCP 목록 | h1·등록 버튼 → 상태 필터(개수 포함) → 표(상태 → 이름 굵게) | 좋음 |
| MCP 상세 | 이름 + 배지 → 호스트:포트(모노)·소유자 → 조치 버튼 → 탭 | 좋음. 종료만 outline인 것은 의도(확인 대화상자가 있는 동작, screens/mcp.md) |

| 로그인 | 제목 + "개발용 OTP 모드" 배지 → 이메일 → 주 버튼 | 좋음 |
| 404 | (고치기 전) 셸 없는 빈 화면에 문장 하나 | **고침**: 셸 안의 h1 + 문장 + 버튼 모양 링크 |

## 3. 일관성

| 요소 | 발견 | 조치 |
|---|---|---|
| 상태 배지 | HEALTHY만 문서 규칙(채움 없음)과 다름 | 고침: 채움 없음, 아이콘 초록, 글자 `fg-muted`. 크기·여백은 그대로라 상태가 바뀌어도 줄이 흔들리지 않음 |
| 흐려진 버튼 | 권한으로 막힌 버튼은 이유를 말하는데, "바뀐 내용 없음"으로 흐려진 저장·변경 취소는 말하지 않음(4개 화면) | 고침: `deny.unchanged` "아직 바뀐 내용이 없어요." 같은 `WithReason` 경로 |
| 명령 팔레트 비활성 항목 | 내비의 같은 항목은 `fg-muted` + 아이콘 60%인데 팔레트만 전체 50% 불투명 | 고침: 내비와 같은 처리 |
| 표 행 조치 버튼의 툴팁 | 이유가 있을 때와 없을 때 다른 컴포넌트(이름 툴팁 / `WithReason`) | 고침: `WithReason` 하나(`label`), 포커스도 유지 |
| 세그먼트 토글 | 이력 기간·스크립트 종류가 같은 `aria-pressed` 묶음·같은 모양 | 좋음 |
| 페이지 머리 동작 | 목록 "MCP 등록"·사용자 "사용자 추가" = 주 버튼, 고지 "전체 화면 미리보기" = outline(보조) | 좋음 |
| 저장 버튼 위치 | 모든 폼에서 마지막 묶음 아래 왼쪽, 저장 → 변경 취소 순서 | 좋음 |

## 4. 밀도

- 관리 화면은 36px 컨트롤, 표 행 44px, 폼 두 열(@container)로 촘촘하되 답답하지 않습니다. 640px 창에서 두 열 폼이 한 열로, 사이드바가 레일로 바뀝니다.
- MCP 설정 폼은 1280×800 창에서 저장 버튼까지 스크롤 두 번입니다(1.4k px). 하단 고정 저장 막대를 검토했지만, 바뀐 칸만 보내는 폼(U27)과 LeaveGuard가 이미 있고 막대가 600px 창에서 본문을 더 가려서 두었습니다(§8-1).
- 보드는 MCP 1개일 때 큰 화면의 대부분이 비지만, 판정 문장이 화면을 지배하므로 "비어 보임"보다 "조용함"으로 읽힙니다. 카드 격자는 `auto-fill`이라 MCP가 늘면 채워집니다.

## 5. 상태 표현

- 6개 상태 모두 아이콘 + 글자 + 색. SUSPECT는 카운트다운 게이지, RECOVERING은 회전 테두리, FAILED는 상단 띠 + soft 채움. 정상과 점검 중은 중립 패널.
- 비어 있음·불러오는 중·오류·준비 중이 화면마다 따로 있습니다: 스켈레톤 + `role=status`, 빈 목록 문장 + 다음 동작, `role=alert` 문장, `PlannedFeature`(점선). 가짜 데이터 없음(U13).
- 실시간: 스트림이 끊기면 상단 바에 "다시 시도 중"(아이콘 + 글자). 다른 사람이 바꾼 설정은 고치지 않은 칸만 바뀌고 폼 위 한 줄이 그 규칙을 알려 줍니다.

## 6. 문구

- 해요체, 짧은 능동형, 사과·느낌표 없음(`ko.test.ts`가 막음). 오류는 무슨 일 + 다음 동작.
- 새 문구 3개: `deny.unchanged` "아직 바뀐 내용이 없어요.", `common.notFoundTitle` "화면을 찾을 수 없어요", `common.notFound` "주소가 틀렸거나 없어진 화면이에요. 주소를 확인하거나 관리 화면 처음으로 가세요."(앞 문장이 무슨 일, 뒤 문장이 다음 동작).
- 남은 어색함 없음. 고지 기본 문구는 공식 안내라 합니다체(의도).

## 7. 고친 것 (고칠 가치가 있다고 본 항목)

1. **정상 배지를 조용하게** — `StatusBadge` HEALTHY 톤을 채움 없음 + 초록 아이콘 + `fg-muted` 글자로. 보드·목록·상세·대시보드 활동이 모두 바뀜. Vitest "keeps HEALTHY quiet (no fill) and fills every problem state"(고치기 전 실패 확인). 대비: `fg-muted`는 bg·surface·surface-raised에서 4.5:1 이상, 상태 아이콘 선은 3:1 이상(Task 6 테스트).
2. **404를 셸 안으로** — h1 + 문장 + 버튼 모양 링크, 내비게이션 유지.
3. **흐려진 저장·변경 취소에 이유** — 위 §3.
4. **팔레트 비활성 항목 가독성** — 위 §3, 대비는 a11y-review.md §3.
5. **포커스를 잃지 않게** — 팔레트를 닫을 때, 이유가 생기거나 사라질 때(a11y-review.md O6·O7).
6. **좁은 창에서 조치 버튼 줄바꿈**, **24px 누름 영역**(정렬 머리, 출력 보기).

기준 이미지는 위 변경 뒤 전체 `pnpm e2e --update-snapshots=all`로 다시 만들고, 바뀐 PNG를 하나씩 열어 확인한 뒤, 업데이트 없이 전체를 한 번 더 돌려 통과를 확인했습니다.

## 8. 검토했지만 고치지 않은 것

1. **하단 고정 저장 막대**(긴 MCP 설정·전역 설정 폼) — §4. 600px 창에서 막대가 본문의 10% 이상을 가리고, 저장하지 않고 떠나면 LeaveGuard가 막습니다. Plan 5 로그 화면을 만들 때 폼 패턴을 다시 볼 때 재검토.
2. **종료 버튼만 outline** — 가장 위험한 동작이 가장 눈에 띈다는 반론이 있지만, 확인 대화상자(destructive 버튼)가 실제 방어선이고 outline은 "다른 종류의 동작"이라는 표시로 screens/mcp.md에 결정돼 있습니다. 유지.
3. **스위치 크기(36×20)** — 접근성 남은 위험 2와 같음.
4. **보드의 빈 공간(MCP 1개)** — 위 §4. 실제 운영에서는 MCP가 여럿입니다.
5. **기준 이미지의 실행 순서 의존** — dashboard·notice-editor 높이가 앞선 spec이 남긴 이력에 따라 달라집니다(Task 15). 이번에도 전체 실행으로만 다시 만들었고, visual 전용 시드는 다음 계획의 E2E 정리로 넘깁니다.
