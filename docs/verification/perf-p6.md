## 4. 한계: 넓은 키워드(W9)

키워드 비용은 **맞는 행 수**에 비례합니다. 그래서 키워드가 많은 행에 맞으면(예: 전체의 30%) **300ms를 넘을 수 있습니다**. 이 경우는 §11 P6 기준에서 뺐고(W9), 테스트로 고정하지 않고 아래처럼 한 번 측정해 기록만 합니다(S4·S9 변형, 같은 100만 건 색인, 워밍업 1번 + 5번 중앙값, 2026-11-07).

| 키워드 | 맞는 행 | 30일 첫 페이지(S4 변형) | 30일 히스토그램(S9 변형) | + 사용자 1명 조건 |
|---|---:|---:|---:|---:|
| `zebra`(기준) | 4,908 (0.5%) | 4.6ms | 3.2ms | 4.6ms |
| `chrome` | 133,654 (13.4%) | 154.2ms | 170.9ms | 26.9ms |
| `tool` | 249,280 (24.9%) | 235.9ms | 252.5ms | 59.6ms |
| `focus` | 400,764 (40.1%) | **301.0ms** | **324.1ms** | 87.0ms |

- 이 데이터에는 정확히 30%에 맞는 낱말이 없어 13%·25%·40%로 곡선을 잽니다. 30% 근처에서 약 250–280ms, 40%에서 300ms를 넘습니다.
- 사용자·세션·카테고리 조건을 함께 걸면 빨라집니다(맞는 행이 줄어듦). 운영 문서(`docs/ops/OPERATIONS.md` ⑥)가 넓은 낱말 대신 사용자·카테고리를 먼저 고르도록 안내합니다.
- 더 빠르게 하려면 키워드 결과에 상한을 두거나 시간 범위를 먼저 좁히는 방식이 필요합니다 — "After Plan 5"(`docs/superpowers/plans/carry-forward.md`)에 남깁니다.

## 5. 다시 재는 법

1. `server/`에서 `uv run python -m pytest -m perf -q`. 캐시(`server/.cache/perf-v1-1000000/`, `perf-purge-v1/`)가 없으면 처음 실행이 데이터를 만들고 색인합니다(수 분, 테스트의 긴 timeout).
