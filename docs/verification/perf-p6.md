3.3의 시간 색인 걷기는 고른 사용자·카테고리에 맞는 행이 적거나 없으면 범위 전체를 걸었습니다("이 두 사람이 X를 한 적이 있나" — 결과 0건이 흔한 질문). 그래서 넓은 키워드 + 여러 값은 이제 두 단계입니다: (1) 범위의 최신 **25,000행**(`WALK_ROWS`)만 시간 색인으로 걸어 한 페이지가 차면 그것이 답(창 밖의 행은 모두 더 오래됨), (2) 차지 않으면 고른 값들의 색인(`ix_events_user`/`ix_events_cat`)을 IN 목록 하나로 읽어 그 행만 MATCH 집합(한 번 만듦)과 대조해 정렬합니다. (1)이 맞는 행 수를 상한까지만 세는 값싼 추정 역할을 합니다. 결과 행은 이전 계획과 같습니다(단위 테스트가 페이지마다 비교).

## 4. 한계: 넓은 키워드(W9)

키워드 비용은 **맞는 행 수**에 비례합니다. 그래서 키워드가 많은 행에 맞으면(예: 전체의 30%) **300ms를 넘을 수 있습니다**. 이 경우는 §11 P6 기준에서 뺐고(W9), 테스트로 고정하지 않고 아래처럼 한 번 측정해 기록만 합니다(S4·S9 변형, 같은 100만 건 색인, 워밍업 1번 + 5번 중앙값, 2026-11-07).

## 5. 다시 재는 법

1. `server/`에서 `uv run python -m pytest -m perf -q`. 캐시(`server/.cache/perf-v1-1000000/`, `perf-purge-v1/`)가 없으면 처음 실행이 데이터를 만들고 색인합니다(수 분, 테스트의 긴 timeout).
2. 결과는 `server/.cache/perf-results.json`(초 단위; `ingest_lines_per_sec`, `purge_rows`, `purge_sec`, `purge_query_p95`).
3. 생성 규칙을 바꾸면 `gen.py`의 `GEN_VERSION`을 올려 캐시를 다시 만듭니다(W39).
4. 실기기(Win 11 Pro)에서는 같은 명령을 저장소 체크아웃에서 돌려 이 표 옆에 적습니다(설치된 묶음에는 테스트가 없습니다).
